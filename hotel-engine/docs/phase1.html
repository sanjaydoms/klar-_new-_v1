Where the rebuild is now — 14 August 2026. This document is the Phase 1 teardown and is kept as written; everything below describes the system as it was. The engine that replaces it now runs end to end — search, hotel detail and rates, destination suggestions, and booking: precheck, commit, confirm, cancel and refund — served over HTTP against PostgreSQL through both supplier adapters, at 722 tests green.
  • Phases 1–8 done — teardown, domain and contracts, supplier layer, search orchestrator, canonical catalogue, detail & rates with the compatibility projection and the HTTP edge, revalidation, and supplier-neutral booking.
  • Booking is one code path. The reference needed 1,013 lines of #commitTripJack and #commitRateGain, picked by a five-clause heuristic over the shape of whatever the browser sent. A test now books through TripJack and through RateGain with the same code, and the browser sends an opaque deal id and the names of the guests — no BookReservation envelope, no supplier protocol.
  • Seven audits have run against the new engine, not only the old one — 48 defects found and fixed in code that was already passing its own tests. The latest ten sit between "the card is charged" and "the room is held": a commit that was retried like a search, a timeout reported as a failure and refunded, a hold answered with a paid booking. Each carries a regression test verified to fail when the fix is reverted. All are listed in docs/OPEN-ISSUES.md §1.
  • Two things must not reach production unresolved — no endpoint authenticates, and no payment gateway is configured. Both are listed in docs/OPEN-ISSUES.md §4.
The three structural failures below are closed by construction: adapters return cost and cannot reach the pricing engine (A), identity is canonical and tiered (B), and every alternative deal stays bookable with its own id (C).

00Executive summary

The existing system is not a naive first attempt. It already contains a supplier registry, a common adapter interface, Redis and L1 caching, request coalescing, circuit breakers, stale-while-revalidate, and a genuinely careful markup and region model. Several files carry excellent reasoning in their comments. That work is worth reading before rebuilding.

But it cannot satisfy the core business requirement — one KLAR search across all suppliers, showing the genuinely lowest price — and it cannot satisfy it for structural reasons, not because of bugs that could be patched.

Structural failure A

Prices are not commensurable

Platform markup is applied to TripJack and not to RateGain, at both search and detail. The “cheapest supplier” test compares TJ net + markup against RG net. The comparison lives inside a deduplicator fed by two adapters that each own their own pricing — there is no layer where a commensurable total exists.

Structural failure B

No canonical hotel identity

The only catalogue is keyed by tjHotelId — a TripJack ID space. Supplier IDs are the identity, and prefixed strings like "TJ:123" travel into the frontend as hotel.id. Cross-supplier matching is 100 m proximity plus a substring name test, per search, in O(n²), with no persisted mapping and no confidence level.

Structural failure C

The alternative deal is unbookable

Merging keeps altDeal: {source, price} — a number and a label. The losing supplier’s rate key, room, board and cancellation terms are discarded at merge time. The shape cannot be extended into a bookable alternative; it has to be replaced.

Everything else in the defect register is downstream of these three.

Recommendation: proceed with the clean-room rebuild. The reference implementation is worth mining for domain knowledge — supplier quirks, real measured latencies, the region and markup failure semantics — and worth discarding as structure.

The pricing block the UI trusts

resolveRatePricing() is the single place the frontend reads a price, and its doc comment records why: several competing totals existed and the detail page picked the pre-markup one, so the B2C margin silently vanished between the card and the review page. The invariant it depends on — basePrice + taxesAndFees === totalPrice — is guaranteed by deriving taxesAndFees rather than summing named parts. Keep both the invariant and the reason.

TripJack search is fundamentally different from RateGain’s: TripJack has no destination search. The adapter resolves the destination to candidate hotel IDs via a Mongo $near over the local catalogue, then densifies — each KLAR page maps to a fixed window of TJ_HIDS_PER_PAGE=150 ids, split into chunks of 50, run 3 at a time, capped at 100 hotels. Yield is roughly 1 bookable hotel per 20 candidate ids. The total returned is the candidate-id count (~6,179 for Goa), not a hotel count.

RateGain search uses a geofilter (or destination code, with a fallback chain), 20 properties per API page, 4 pages fetched concurrently per KLAR page.

Two schema-level blockers for “add Supplier C without a rewrite”:

  • BookingProvider is a two-value enum. A third supplier requires a schema migration.
  • Supplier payloads live in named columns and are read directly by the frontend. A third supplier requires a new column and frontend changes.

There is no canonical hotel table, no supplier-mapping table, no destination-mapping table beyond RGDestination, and no supplier-configuration table — all supplier behaviour is environment variables.

05What the reference gets right

Recorded deliberately, because the rebuild should not lose it.

  1. products.service.ts — 21 lines, zero supplier knowledge, pure registry dispatch. The target shape for every orchestrator.
  2. buildPublicPricing() derives taxesAndFees from total − base, so the breakdown cannot fail to add up.
  3. ratePricing.ts — one function, one place the client reads a price.
  4. deriveRefundable() distinguishes “non-refundable” from “unknown”, and adapters emit undefined rather than a fabricated false.
  5. Markup config failure semantics: fresh → live → stale → env, never silently to zero, with “configured off” distinct from “never configured”.
  6. Region-keyed markup snapshots rather than a module-level “current region”, with the concurrency corruption explained in the comment.
  7. Facet accumulation — cumulative across pages, computed on the unfiltered set.
  8. Commit-path safety: idempotency key + unique index, Redis lock, payment-reuse guard, b2cPriceFloor, idempotent refund claim, reconciliation worker.
  9. Measured supplier latencies in comments: RateGain bestproperties ≈ 10.7 s domestic, ≈ 14.2 s international geofilter. Real operational knowledge — it should drive the new deadline budget.
  10. Request coalescing for both master builds and master extensions.

06Defect register

Twenty-four findings, ordered by commercial impact. Locations refer to the extracted reference tree.

Critical — money & correctness5
D-1Platform markup applied to one supplier onlytripJackAdapter.ts:278 · rateGainAdapter.ts:474

Two consequences:

  • The cheapest-deal comparison compares TJ net + platform markup against RG net.
  • hotel-booking-service does apply platform markup to RateGain (rategain.adapter.ts:117). A RateGain booking is therefore quoted without the markup and validated with it — a systematic quote-vs-charge divergence on one supplier.
D-2Price comparison ignores rate equivalencededuplicator.ts:89-92

currentPrice < existingPrice and nothing else. Meal plan, refundability, cancellation deadline, room type, occupancy and taxesIncluded are not consulted. A non-refundable room-only rate will beat a refundable breakfast-inclusive rate, and the customer will never know a comparison happened.

D-3Contradictory taxesIncluded semanticstripJackAdapter.ts:300-305 · rateGainAdapter.ts:445

The TripJack comment says “totalPrice already includes all taxes… taxesIncluded = true” and the next line sets taxesIncluded: false. RateGain infers it as taxAmt === 0, conflating “tax-inclusive” with “tax field absent”. Two suppliers with different, partly-wrong tax semantics feed one comparison.

D-4The alternative deal is unbookablededuplicator.ts:96,104

altDeal = { source, price }. The loser’s rawPayload, rate key, board, room and cancellation policy are discarded and cannot be recovered without re-searching.

D-5Region is derived and then discardedtripJackAdapter.ts:289 vs :278

deriveRegion(h.country) is computed and stored as markupRegion, but platformMarkupAmount(tjBase) is called with no region argument, defaulting to "ALL". The region-aware markup exists, is documented, is tested, and is not used at search time.

D-6Supplier IDs are the identity, everywhere

"TJ:…"｜"RG:…" is the frontend’s primary key, the /products routing key, the precheck routing key and the commit routing key. No canonical layer exists.

07Target architecture

Principles

  1. One commensurable price object. No comparison ever happens on a number a supplier adapter produced. Adapters emit supplier cost; one pricing engine converts cost → customer price; only customer prices are compared.
  2. Canonical identity before merge. Hotels are matched to a persisted klarHotelId with an explicit confidence level. Unmatched is a valid, safe outcome — duplicates beat false merges.
  3. Deals, not prices. A merged hotel carries deals[] of complete, bookable offers. The winner is a selection over that set, not a mutation of it.
  4. Supplier code appears in exactly two places — inside suppliers/<code>/, and as an opaque string in persisted records. Nowhere in orchestration, the API contract, or the frontend.
  5. Honesty over optimism. If a supplier did not answer, the response says so and does not claim the price is the lowest available.

  supplierTotal: number;
  platformMarkup: number;

  taxesAndFees: number;
  total: number;                      // the ONLY comparable number
  perNight: number;  nights: number;
  breakdown: PriceLine[];             // audit trail, sums to total
}

  dealId: string;                     // KLAR-issued, opaque, resolvable
  supplier: string;
  klarHotelId: string;  supplierHotelId: string;

}

interface MergedHotel {
  klarHotelId: string;
  hotel: CanonicalHotel;
  featuredDeal: SupplierDeal;         // a POINTER INTO deals[], not a copy
  deals: SupplierDeal[];              // ALL deals, all suppliers, bookable

  };

}

Because featuredDeal points into deals[], nothing is discarded at merge time — D-4 becomes structurally impossible.

}

interface SupplierSearchResult {
  supplier: string;

  responseTimeMs: number;
  error?: NormalizedSupplierError;
}

Two deliberate departures from the brief’s sketch:

  • precheck/book/cancel are required, not optional. A supplier that cannot be booked has no place in a search that promises the lowest bookable price. Capability variation belongs in capabilities, not in omitted methods.
  • Adapters return SupplierCost, never CustomerPrice. This is the single change that makes D-1 impossible to reintroduce: there is no code path where an adapter can add markup.

Search pipeline

POST /api/search/hotels/search
  ├─ 1  Validate & canonicalise request
  ├─ 2  Resolve destination → CanonicalDestination (+ per-supplier refs)
  ├─ 3  Cache lookup (static/dynamic split)
  ├─ 4  Select suppliers: registry + admin config + capability + coverage
  ├─ 5  FAN OUT — Promise.allSettled under ONE absolute deadline
  │        TripJack ──▶ cost-only SupplierHotel[]
  │        RateGain ──▶ cost-only SupplierHotel[]
  ├─ 6  Match      → klarHotelId + confidence          [modules/matching]
  ├─ 7  Price      → SupplierCost → CustomerPrice      [modules/pricing]
  ├─ 8  Merge      → MergedHotel { deals[] }
  ├─ 9  Compare    → equivalence classes → featuredDeal
  ├─ 10 Filter → Sort → Paginate (stable cursor)
  └─ 11 Respond, including supplier health for this search

Steps 6 and 7 are separate and ordered. Matching never sees a price; pricing never sees another supplier. Comparison is the only step that sees both, and by then every number is a CustomerPrice.total in the same currency.

Deadline strategy

  • One absolute deadline per search, not per call, derived from measured latency — RateGain international geofilter ≈ 14.2 s is the binding constraint.
  • Suppliers run concurrently and are not cancelled because another finished. A supplier is cancelled only when it exhausts its own budget or the search deadline passes.
  • On deadline, return what is held and label it:
"comparison": {
  "comparedAcross":      ["TJ"],
  "incompleteSuppliers": ["RG"],
  "priceGuarantee":      "PARTIAL"     // BEST_AVAILABLE | PARTIAL
}

The UI can then say “best of the suppliers that responded” instead of implying a guarantee the system did not earn. Late supplier results are not discarded — they land in the cache, so the next request sees the complete picture.

Rate tokens

The frontend must never hold supplier state, and the backend must never re-search at booking time.

dealId  →  Redis: sealed RateToken
              { supplier, supplierHotelId, supplierRateRef,
                correlationId, reviewHash, occupancy, board,
                quotedCost, quotedPrice, pricingContext, issuedAt, expiresAt }

dealId is opaque, signed and short-lived. The client sends it to precheck and commit; the booking engine resolves it to the owning supplier and its native state. This kills D-6, D-9 and the frontend’s BookReservation construction in one move — the client never learns which supplier it is booking.

  • Name normalisation strips chain prefixes, punctuation, diacritics and legal suffixes, then compares by token-set ratio — not substring containment, which is what makes D-7 wrong.

  • A confirmed tier-3/4 match is written back, so the second search for that destination is a tier-1 lookup.

Comparability — an explicit business rule, not an accident

Deals are grouped into equivalence classes before a winner is chosen. Default class key:

(occupancy, board.code, refundability tier, roomCategory)
  1. Group deals[] into equivalence classes.
  2. Within each class, cheapest CustomerPrice.total wins.
  3. featuredDeal = the winner of the class matching the product’s configured preference (default: the class the search requested; ties broken by refundable > non-refundable, then supplier reliability).
  4. All other class winners remain in deals[] and surface as “other rates”.

ABSOLUTE_CHEAPEST is available as a configured policy, not a silent default.

Pricing engine

SupplierCost
   → normalise currency (single FX source, rate + timestamp recorded)
   → normalise tax semantics (taxesIncludedInBase made explicit per supplier)
   → + platform markup      (region-aware, per supplier, from config)
   → + channel markup       (B2C margin | B2B agent rules)
   → + applicable fees
   = CustomerPrice          ← the ONLY comparable number
  • Applied uniformly across all suppliers by one engine. No adapter may call it.
  • Region passed explicitly through the whole chain, never defaulted.
  • base + taxesAndFees === total enforced by construction and asserted in tests.
  • Every markup step recorded in breakdown[], so any price can be explained after the fact.

10Decisions needed before Phase 2

These change the design, so they need answers rather than assumptions. Where there is a recommendation it is stated first.

All eight answered. The questions are kept below as the record of what Phase 1 asked. All eight were adopted as recommended defaults in ADR-0000 so Phase 2 could start, each with a stated cost to reverse. The three that were commercial rather than technical were then confirmed by KLAR on 13 Aug 2026 and promoted from assumption to decision in ADR-0007.
  • Q1 Comparability confirmed — compare within equivalence classes, as recommended. ABSOLUTE_CHEAPEST stays a configured policy, never a default.
  • Q2 RateGain markup confirmed — applied uniformly to every supplier, at search and at booking. This was the one live commercial risk on the page; D-1 is now closed by construction, since adapters return cost and cannot reach the pricing engine.
  • Q3 Partial results confirmed — the UI may say “best of the suppliers that responded”. The deadline stays a deadline.
  • Q4 Deadline — 15 s hard, 12 s soft, 14 s per supplier, from the measured RateGain figures above (ADR-0003).
  • Q5 Topology · Q6 Datastore — one hotel-api deployable with in-repo module boundaries; PostgreSQL as system of record (ADR-0005).
  • Q7 Static content — no neutral source licensed, so the catalogue stays TripJack-derived and match tier 2 is inert. externalIds is reserved so it activates without a model change if that changes (ADR-0000 §7). Still the highest-leverage open input to match quality.
  • Q8 B2B — B2C first, but Channel is first-class in the domain from day one, so B2B is a pricing configuration rather than a second code path.
  1. Comparability policy. Recommend: compare within equivalence classes, surface other classes as alternative rates. Confirm — or state that KLAR wants absolute cheapest regardless of board and refundability.
  2. RateGain platform markup (D-1). Search omits it; booking applies it. Which is the intended commercial behaviour? This determines whether live RateGain revenue is currently being under-collected or the bookings are over-charging.
  3. Partial-result honesty. Confirm the UI may show “best of the suppliers that responded”. If it must always claim a guarantee, the deadline becomes a hard wait and latency rises accordingly.
  4. Search deadline budget. Measured RateGain international geofilter ≈ 14.2 s. What is the maximum acceptable time-to-first-result?
  5. Rebuild target. Single hotel-api service, or keep the search/booking split? Recommend a single deployable with internal module boundaries — the split is what produced the divergence in §01.
  6. Stack constraints. Node/TypeScript is given. Keep MongoDB, or move canonical identity and bookings to Postgres? Recommend Postgres for canonical/booking (relational integrity on mappings and money) with Mongo retained for the property catalogue — but this is a real operational decision.
  7. Static-data source. The catalogue is TripJack-derived. Is a supplier-neutral content source (GIATA or equivalent) available? It would move most matching to tiers 1–2 and is the single highest-leverage input to match quality.
  8. B2B scope. The reference carries a full B2B/agent-wallet path. Is B2B in scope for this rebuild, or B2C-only with B2B to follow?
